# Задание 1. Исследование моделей и инфраструктуры

Дата анализа: 7 августа 2026 года.

## 1. Контекст и критерии выбора

QuantumForge Software требуется корпоративный RAG-бот для поиска по технической и организационной документации. База знаний содержит около 18 000 Markdown/MDX-файлов, 3 000 страниц Confluence и 250 PDF-документов и растёт примерно на 400 страниц в месяц. Пользователи задают как общие вопросы, так и запросы с точными идентификаторами: названиями сервисов, версиями API, номерами ошибок и тикетов.

При выборе стека необходимо учитывать не только качество модели, но и:

- конфиденциальность документов и правила передачи данных внешним провайдерам;
- поддержку английского, русского и программного кода;
- задержку одного ответа и пропускную способность под нагрузкой;
- стоимость API либо совокупную стоимость владения локальной инфраструктурой;
- возможность обновлять документы, удалять устаревшие версии и фильтровать результаты по метаданным;
- существующую инфраструктуру компании в AWS и Kubernetes.

Количество документов само по себе недостаточно для точного sizing. Перед production-пилотом необходимо измерить реальное число чанков, среднюю длину запроса и ответа, пиковую частоту запросов, требуемую параллельность, темп переиндексации и целевые показатели времени ответа.

Для сравнения вариантов предполагается, что качество проверяется на наборе из 50–100 корпоративных вопросов. Для retrieval измеряются как минимум Recall@k и MRR, а для итогового ответа — корректность, наличие подтверждающей ссылки и доля правильных отказов «Я не знаю».

## 2. Сравнение LLM

### 2.1. Локальные и облачные модели

| Вариант | Качество ответа | Скорость | Стоимость владения | Развёртывание и ограничения |
| --- | --- | --- | --- | --- |
| Qwen3-4B Q4_K_M локально | Достаточно для PoC, поддерживает более 100 языков, код и следование инструкциям. Уступает крупным облачным моделям в сложном анализе и устойчивости к противоречивому контексту | На Apple Silicon отсутствует сетевая задержка, но скорость и параллельность ограничены памятью и вычислительными ресурсами устройства | API-затраты отсутствуют, но остаются стоимость оборудования, электричества, сопровождения, мониторинга и обновлений | Можно запускать через Ollama, llama.cpp или Docker Model Runner. Данные не покидают устройство |
| OpenAI GPT-5.6 Luna | Высокое качество для хорошо определённых задач; сильная многоязычность и хорошее следование инструкциям | Не требуется своё GPU; задержка зависит от сети, лимитов API и нагрузки провайдера. Высокая масштабируемость | Оплата по токенам: $1 за 1 млн входных и $6 за 1 млн выходных токенов | Самое простое подключение по API. Необходимы юридическая проверка, политика хранения данных и контроль передаваемого контекста |
| OpenAI GPT-5.6 Terra | Выше качество на сложных запросах, чем у экономичного варианта; подходит для неоднозначных архитектурных и аналитических вопросов | Облачная масштабируемость, но цена и время reasoning выше | $2,50 за 1 млн входных и $15 за 1 млн выходных токенов | Простое API-развёртывание; для типовых RAG-вопросов может быть избыточна |
| YandexGPT Lite 5 / Pro 5.1 | Lite ориентирована на быстрые типовые задачи, Pro — на анализ и RAG. Особенно сильны в русскоязычных сценариях | Облачное исполнение снимает потребность в GPU; в общем инстансе время ответа может меняться при высокой нагрузке | Синхронный режим без НДС: Lite — $1,639344 за 1 млн входных или выходных токенов; Pro 5.1 — $6,557376 | Доступны API генерации и OpenAI-совместимые API. Для финско-эстонской компании требуется отдельная проверка доступности поставщика, договора и требований к данным |

Облачная модель не всегда быстрее локальной по времени до первого токена: маленькая локальная модель не тратит время на сетевой запрос. При этом облачный провайдер обычно выигрывает по качеству, общей пропускной способности и числу параллельных запросов. Поэтому необходимо отдельно измерять:

- TTFT — время до первого токена;
- скорость генерации в токенах в секунду;
- полное время ответа;
- производительность и стабильность задержки при параллельной нагрузке.

Согласно документации, Qwen3-4B содержит 4 млрд параметров, поддерживает более 100 языков и имеет нативный контекст 32 768 токенов. Квантование Q4_K_M уменьшает расход памяти и даёт приемлемый баланс качества и скорости для MacBook с 8 ГБ unified memory. Llama 3.2 3B также помещается на таком устройстве, но русский язык не входит в перечень её официально поддерживаемых языков, поэтому для многоязычного PoC выбран Qwen3-4B.

### 2.2. Пример расчёта облачной стоимости

Для иллюстрации предположим 1 000 запросов в день, по 3 000 входных и 500 выходных токенов на запрос. За 30 дней получится 90 млн входных и 15 млн выходных токенов.

Расчёт по тарифам синхронного режима:

| Модель | Вход, за 1 млн токенов | Выход, за 1 млн токенов | Ориентировочно в месяц |
| --- | ---: | ---: | ---: |
| OpenAI GPT-5.6 Luna | $1 | $6 | 90 × $1 + 15 × $6 = **$180,00** |
| OpenAI GPT-5.6 Terra | $2,50 | $15 | 90 × $2,50 + 15 × $15 = **$450,00** |
| YandexGPT Lite | $1,639344 | $1,639344 | 105 × $1,639344 = **$172,13** |
| YandexGPT Pro 5.1 | $6,557376 | $6,557376 | 105 × $6,557376 = **$688,52** |

Расчёт не включает повторные запросы, дополнительные проверки ответа, кешированные токены, токены инструментов и налоги. Он показывает, что YandexGPT Lite и GPT-5.6 Luna близки по стоимости выбранного профиля нагрузки, поэтому окончательный выбор между ними следует делать по результатам eval, требованиям к языкам, доступности поставщика и политике работы с данными. Цены необходимо перепроверить непосредственно перед production-запуском.

### 2.3. Вывод по LLM

Для учебного PoC выбирается **Qwen3-4B Q4_K_M**: модель работает локально, поддерживает нужные языки и укладывается в ограничение ноутбука при небольшом контексте и одном пользователе.

Для production рекомендуется не фиксировать поставщика до проведения eval. Базовый кандидат для разрешённых к отправке данных — экономичная облачная модель, например GPT-5.6 Luna. Конфиденциальные запросы должны обрабатываться локальной моделью внутри контролируемого контура.

## 3. Сравнение моделей эмбеддингов

Модель эмбеддингов используется дважды: при индексации документов и при обработке каждого пользовательского запроса. Документы и запросы должны кодироваться совместимыми моделями; одинаковая размерность векторов не делает векторные пространства разных моделей совместимыми.

| Вариант | Скорость создания индекса | Качество поиска | Стоимость и ограничения |
| --- | --- | --- | --- |
| all-MiniLM-L6-v2 | Очень высокая скорость, небольшой расход памяти | Хороший baseline для коротких англоязычных текстов. Вход длиннее 256 word pieces обрезается; не является предпочтительным вариантом для русскоязычного и смешанного корпуса | Бесплатные веса, 384 измерения. Минимальные требования к железу |
| multilingual-e5-small | Быстрая работа на CPU и умеренный расход памяти | Поддерживает около 100 языков, подходит для многоязычного semantic search | Бесплатные веса, 384 измерения. Требует использовать корректные префиксы `query:` и `passage:` |
| Qwen3-Embedding-0.6B | Медленнее небольших MiniLM/E5, но пригодна для локальной пакетной индексации | Поддерживает более 100 языков, длинный контекст и поиск по программному коду. Позволяет выбирать выходную размерность до 1024 | Бесплатные веса, но сама модель и индекс требуют больше RAM. На M1 целесообразно проверить 512 и 1024 измерения |
| OpenAI text-embedding-3-small | Индексация выполняется облачно и хорошо масштабируется пакетами; есть сетевая задержка | Стабильное универсальное качество без локального ML-инференса | $0,02 за 1 млн токенов. Документы передаются внешнему провайдеру |
| Yandex Text Embeddings v2 | Облачная индексация без собственного ML-сервера | Отдельные модели для документов и запросов; размерность 128, 256, 512 или 768 | $0,0000827869 за 1 000 токенов без НДС по опубликованному тарифу. Требуется внешняя передача текста |

Большая размерность не гарантирует более качественный поиск: результат определяется обучением модели, языком и доменом данных. При этом размерность прямо влияет на размер индекса. Например, 500 000 векторов `float32` без учёта служебных структур занимают приблизительно:

- 384 измерения — 768 МБ;
- 512 измерений — 1,02 ГБ;
- 1024 измерения — 2,05 ГБ.

Если условный корпус содержит 50 млн токенов, первичная индексация через OpenAI text-embedding-3-small будет стоить около $1. Для Yandex Text Embeddings по опубликованному тарифу — около $4,14. Это показывает, что выбор локальных эмбеддингов следует аргументировать прежде всего конфиденциальностью, автономностью и контролем, а не только ценой первичной индексации.

Для PoC выбирается **Qwen3-Embedding-0.6B**, поскольку база содержит естественный язык и программный код. Первичный baseline строится с размерностью 512, затем на одном eval-наборе сравниваются 512 и 1024. Если одновременная работа embedding-модели и LLM вызывает swap на ноутбуке, запасным вариантом будет multilingual-e5-small.

## 4. Сравнение ChromaDB и FAISS

FAISS в строгом смысле является библиотекой поиска по векторам, а не самостоятельной базой данных. Это важно учитывать при сравнении: документы, метаданные, контроль доступа и жизненный цикл индекса для FAISS реализуются приложением.

| Критерий | FAISS | ChromaDB |
| --- | --- | --- |
| Скорость поиска и индексации | Большой выбор точных и приближённых индексов, высокая производительность CPU/GPU. Для небольшого PoC подходит точный `IndexFlatIP` с нормализованными векторами | Достаточная производительность для PoC и средних нагрузок; детали хранения и индекса скрыты за API |
| Сложность внедрения | Минимум зависимостей, индекс находится внутри Python-приложения. Хранение исходного текста и метаданных нужно реализовать отдельно | Готовые коллекции, persistence, CRUD, API и серверный режим уменьшают объём прикладного кода |
| Поддержка | Нет отдельного сервиса, а значит меньше операционной нагрузки. Обновление, удаление и резервное копирование индекса остаются задачей приложения | Появляется отдельный компонент, который нужно обновлять, мониторить и резервировать |
| Фильтрация и метаданные | Нет встроенного механизма уровня БД; фильтрация реализуется до или после поиска либо отдельным хранилищем | Есть metadata filtering, что удобнее для версий, источников, подразделений и ACL |
| Масштабирование | Масштабирование и параллельный доступ проектируются самостоятельно | Поддерживаются локальный, single-node и distributed режимы |
| Стоимость владения | Лицензия бесплатна, для PoC не нужен отдельный сервер. При усложнении требований растёт объём собственного кода | Лицензия бесплатна, но серверный режим требует CPU, RAM, диска и сопровождения |

### 4.1. Выбор для проекта

Для учебного PoC выбирается **FAISS** по следующим причинам:

- он прямо предусмотрен условиями проекта;
- не требует отдельного сервиса и экономит память на ноутбуке;
- объём демонстрационного корпуса невелик;
- позволяет явно показать этапы создания embeddings и similarity search.

FAISS будет встроен в контейнер приложения, а файл индекса и метаданные будут храниться в подключаемом volume. Отдельный контейнер «FAISS-сервер» не нужен, поскольку FAISS — библиотека.

Для production-пилота стоит дополнительно оценить Qdrant. Он предоставляет развитую фильтрацию, payload indexes, API и удобный контейнерный запуск, но не является «бесплатным в поддержке»: self-hosted-инсталляции нужны аутентификация, TLS, резервное копирование, мониторинг и при необходимости репликация. В рамках этого задания Qdrant остаётся направлением развития и не заменяет обязательное сравнение ChromaDB и FAISS.

## 5. Варианты инфраструктуры

### 5.1. Сравнение конфигураций

| Вариант | CPU | RAM | GPU | Диск | Стек и назначение |
| --- | --- | --- | --- | --- | --- |
| 1. Локальный учебный PoC | Apple M1 | 8 ГБ unified memory | Встроенный Apple GPU через Metal | Не менее 30–50 ГБ свободного SSD | Qwen3-4B Q4, Qwen3-Embedding-0.6B, FAISS, один разработчик и последовательная обработка запросов |
| 2. Полностью облачные модели | 4 vCPU | 16 ГБ | Не требуется | 100 ГБ SSD | Бот и индекс на CPU; LLM и embeddings через OpenAI/Yandex API. Минимальная эксплуатация, но данные покидают контур |
| 3. Гибридная production-конфигурация | 8 vCPU | 32 ГБ | Не требуется для основного маршрута | 200 ГБ NVMe | Документы, embeddings и векторное хранилище внутри AWS; облачная LLM только для разрешённых данных. Лучший баланс стоимости, качества и контроля |
| 4. Полностью закрытый контур | 16 vCPU | 64 ГБ | NVIDIA L4/A10 с 24 ГБ VRAM | 500 ГБ NVMe | Локальная LLM 7B/8B, локальные embeddings и векторная БД. Максимальный контроль, но самые высокие расходы и сложность |

Указанные конфигурации являются стартовыми для пилота, а не гарантированной production-ёмкостью. Они должны быть подтверждены нагрузочным тестом. Если требуется высокая доступность, к расчёту добавляются как минимум вторая реплика приложения, реплика векторного хранилища и запас ресурсов на отказ одного узла.

### 5.2. Выбор лучшего варианта

Для реальной QuantumForge рекомендуется **вариант 3 — гибридная архитектура**:

1. Исходные документы, ACL, версии и метаданные остаются внутри существующего AWS-контура.
2. Embeddings строятся внутри контура, чтобы не передавать весь корпус внешнему провайдеру.
3. Retrieval выполняется локально с обязательной фильтрацией по доступу пользователя и актуальной версии документа.
4. Маршрутизатор классифицирует запрос и найденный контекст до обращения к LLM.
5. Разрешённые данные отправляются экономичной облачной LLM.
6. Конфиденциальные данные направляются локальной LLM либо запрос завершается контролируемым отказом, если локальный маршрут недоступен.

Такой вариант использует качество и масштабируемость облачных моделей, но не требует держать дорогое GPU для всех запросов. Полностью закрытый вариант оправдан только в случае запрета на передачу любого контекста внешним поставщикам.

## 6. Итоговая конфигурация учебного PoC

Для реализации на MacBook Air M1 8/256 выбран следующий стек:

- **LLM:** Qwen3-4B в квантовании Q4_K_M;
- **модель эмбеддингов:** Qwen3-Embedding-0.6B, начальная размерность 512;
- **векторный индекс:** FAISS CPU, для baseline — `IndexFlatIP` и нормализованные embeddings;
- **запуск LLM:** Ollama или llama.cpp на macOS с Metal; допустим Docker Model Runner с Metal;
- **приложение:** Python/LangChain и Telegram-бот в Docker;
- **хранение:** файл FAISS и метаданные в persistent volume.

На устройстве с 8 ГБ unified memory LLM, embedding-модель, macOS, Docker и IDE используют одну память. Поэтому контекст LLM на первом этапе следует ограничить 4–8 тысячами токенов, не запускать тяжёлые 7B-модели и контролировать swap. Индексация выполняется отдельным пакетным этапом, однако embedding-модель должна оставаться доступной и после индексации, потому что каждый пользовательский запрос необходимо преобразовать в то же векторное пространство.

## 7. Риски и меры контроля

| Риск | Мера контроля |
| --- | --- |
| Бот отвечает по похожему, но не отвечающему на вопрос чанку | Калибруемый порог retrieval, answerability check и правильный ответ «Я не знаю» |
| В выдачу попадает устаревшая версия | Стабильные `source_id`, версии, `status=current`, удаление или замена старых чанков |
| Несколько копий документа занимают весь контекст | Дедупликация при ingestion, канонический источник, группировка результатов по документу |
| Пользователь получает закрытый документ | Фильтрация по ACL до vector search или во время него; запрет полагаться только на промпт LLM |
| Semantic search не находит точный код ошибки | Hybrid search: BM25 для идентификаторов плюс embedding search для смысла, затем rank fusion или reranking |
| На ноутбуке заканчивается память | Уменьшение контекста и размерности embedding, переход на multilingual-e5-small, последовательная обработка запросов |
| Стоимость облачного API растёт | Лимиты токенов, кеширование, мониторинг стоимости, маршрутизация типовых запросов на более дешёвую модель |

## 8. Заключение

Для учебного проекта оптимальна полностью локальная конфигурация **Qwen3-4B Q4_K_M + Qwen3-Embedding-0.6B + FAISS**. Она соответствует ограничениям MacBook Air M1, не требует оплаты API и позволяет продемонстрировать полный RAG-процесс.

Для production в QuantumForge лучшей является гибридная конфигурация: локальное хранение документов, embeddings и retrieval внутри AWS, облачная LLM для разрешённого контента и локальный маршрут для конфиденциальных данных. FAISS подходит для PoC, но при появлении требований к многопользовательской работе, сложной фильтрации, репликации и обновлению данных следует провести отдельное сравнение ChromaDB и Qdrant на корпоративном eval-наборе.
