# Задание 6. Ежедневное обновление базы знаний

## Результат

Источником остаётся локальная папка `Task2/knowledge_base`. Автор добавляет,
изменяет или удаляет Markdown-файлы, а `app/update_index.py` синхронизирует с
ними SQLite и FAISS. Подготовлен ежедневный запуск в 06:00 через cron, но по
условию текущего прогона он **не установлен и не активирован**.

Основные артефакты:

- `app/update_index.py` — безопасная точка входа для планировщика;
- `Task6/crontab.example` — готовая cron-запись;
- `Task6/com.quantumforge.ragbot.plist.example` — launchd-конфигурация бота;
- `Task6/architecture.puml` — архитектура и поток данных;
- `Task6/example-index-update.jsonl` — пример реального обновления.

## Как работает обновление

Скрипт повторно использует инкрементальный индексатор из задания 3 вместо
создания второго пайплайна:

1. Сканирует `Task2/knowledge_base/*.md`.
2. Сравнивает SHA-256 каждого файла с хэшем в SQLite.
3. Неизменившиеся документы пропускает без генерации эмбеддингов.
4. Новые и изменённые документы разбивает через
   `RecursiveCharacterTextSplitter`: 500 токенов, overlap 50 токенов.
5. Создаёт нормализованные 512-мерные эмбеддинги моделью
   `Qwen/Qwen3-Embedding-0.6B` и сохраняет чанки с метаданными в SQLite.
6. Удаляет из SQLite документы, исчезнувшие из исходной папки, и атомарно
   заменяет производный FAISS-файл.
7. Проверяет целостность SQLite и точное совпадение количества и ID чанков в
   SQLite и FAISS.

Если изменений нет, FAISS-файл не перезаписывается. Это сокращает лишний I/O и
не вызывает ненужный перезапуск бота.

## Ручной запуск

Из корня репозитория:

```bash
venv/bin/python -m app.update_index
```

Рабочий JSONL-лог по умолчанию записывается в
`Task6/logs/index-update.jsonl`. Каждое событие содержит UTC timestamp. Итоговое
событие `update_completed` содержит число новых чанков, общее число документов
и чанков, размер FAISS-файла, продолжительность, число ошибок и факт перезапуска
бота.

## Ошибки и параллельные запуски

- Межпроцессный `flock` не допускает двух одновременных обновлений. Второй
  процесс пишет `update_skipped` и завершается успешно.
- Индексация и валидация повторяются до трёх раз с паузой 5 секунд.
- Каждая неудачная попытка записывается как `update_attempt_failed`; после
  исчерпания попыток процесс пишет `update_failed` и возвращает код `1`.
- Ошибка перезапуска бота также даёт ненулевой код, чтобы её увидел
  планировщик.
- В логах нет текстов документов, запросов, токенов или содержимого `.env`.

## Планировщик и бот

`Task6/crontab.example` запускает обновление ежедневно в 06:00 по локальному
времени macOS. В нём используются абсолютные пути, потому что окружение cron
минимально. Stdout/stderr планировщика направлены в
`Task6/logs/scheduler.log`, а структурированные события отдельно сохраняются
самим Python-скриптом.

Telegram-бот читает FAISS в память при запуске. Поэтому после успешного
изменения индекса updater выполняет:

```bash
/bin/launchctl kickstart -k gui/$(id -u)/com.quantumforge.ragbot
```

`KeepAlive` в launchd-шаблоне также запускает бота снова, если его процесс
аварийно завершился. При no-op обновлении `kickstart` не вызывается.

Конфигурации пока являются только шаблонами. Когда понадобится включить
автоматизацию, сначала нужно создать каталог логов, проверить plist и загрузить
launch agent, затем добавить cron-запись:

```bash
mkdir -p Task6/logs
plutil -lint Task6/com.quantumforge.ragbot.plist.example
cp Task6/com.quantumforge.ragbot.plist.example ~/Library/LaunchAgents/com.quantumforge.ragbot.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.quantumforge.ragbot.plist
crontab -l > /tmp/quantumforge-crontab
cat Task6/crontab.example >> /tmp/quantumforge-crontab
crontab /tmp/quantumforge-crontab
```

Эти команды приведены для будущей установки и в рамках задания не
выполнялись. Перед установкой стоит убедиться, что в существующем crontab ещё
нет такой же строки. На ноутбуке cron не разбудит спящий Mac; пропущенный запуск
состоится только на следующий день. Для production-подобного macOS-сценария
расписание можно также перенести в launchd `StartCalendarInterval`.

## Проверка

Автотесты покрывают успешный запуск, no-op, retry, окончательную ошибку,
конкурирующий запуск и расхождение ID между SQLite и FAISS:

```bash
venv/bin/python -m pytest app/tests/test_update_index.py
```

Интеграционная проверка выполняется добавлением временного Markdown-документа,
запуском updater, поиском уникального факта, удалением документа и повторным
запуском updater. Временный документ после проверки в базе знаний не остаётся.

Фактический результат текущего прогона:

- новый документ дал 1 новый чанк, после обновления было 38 документов и 54
  чанка;
- запрос `When is the Clockwork Finch calibrated?` нашёл новый документ первым
  со score `0.775`;
- после удаления updater зафиксировал `deleted_documents=1`, вернул индекс к 37
  документам и 53 чанкам, а контрольная строка исчезла из SQLite;
- `bot_restarted=false`, потому что launchd-сервис намеренно не включался.

Полные структурированные события сохранены в
`Task6/example-index-update.jsonl`.

## Диаграмма

PlantUML-файл можно отрендерить локально:

```bash
plantuml Task6/architecture.puml
```

Для учебного проекта замена FAISS через временный файл достаточна. В системе с
несколькими экземплярами API лучше публиковать версионированный snapshot
`SQLite + FAISS` и атомарно переключать указатель на целую версию, чтобы все
реплики одновременно видели согласованную пару файлов.
